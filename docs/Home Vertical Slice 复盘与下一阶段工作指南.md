## 1. 复盘范围

本复盘综合了以下信息：

- 当前 Home vertical slice 的完整 Codex 任务记录；

## 3. 过程回顾

### 阶段 A：参考网站与能力拆解

先分析参考网站的 Header、手绘圆圈、状态机、滚动动画和自由拖拽，再判断哪些效果可以由 Figma 表达，哪些必须进入代码验证。这一步建立了正确的技术方向，也促成了 vertical slice 的工作方法。

### 阶段 B：Home 首版实现

使用 Figma、真实素材和开发 Prompt 快速搭建了 Home 首版，并部署为可访问网站。首版证明了 Header、滚动、拖拽和主题切换可以落地，但没有在开发前完全冻结素材边界、组件状态和视觉验收基准。

### 阶段 C：Header 密集校准

大量迭代集中在：

- Home 默认和 Hover 图标尺寸；
- Projects 插画容器、SVG viewport 与裁切；
- 手绘圆圈比例与绘制动画；
- Contact 命中范围及二级 Hover；
- About 插画、圆圈比例和垂直位置；
- 字体、颜色、语言/主题图标；
- Notes 插画和施工中提示。

Git 历史显示，前 31 个提交主要用于 Header、字体、颜色、开关和 Avatar 等共享基础，占全部 42 个提交约 74%。这不是无效工作——这些细节最终构成了网站的品牌体验——但说明共享组件应在下一个页面开始前先冻结和提取。

### 阶段 D：内容与素材管理

后期才把页面文字、Project、Notes 和 Home 图片逐步迁移到 Markdown。这一阶段显著改善了网站的长期维护性，也证明“内容与布局分离”是正确方向。如果这套内容合同在 Home 开发前就锁定，部分代码返工可以避免。

### 阶段 E：图片堆与响应式交互

通过真实浏览器截图和多视口测试，逐步完成：展开布局、统一间距、中心轴、拖拽边界、稳定倾斜角度和可逆滚动状态。这部分采用“视觉证据 + 指标 + 回归验证”的方式后，迭代质量明显高于早期仅凭代码尺寸判断的阶段。

## 4. 做得好的地方

### 4.1 Vertical slice 的策略是正确的

先完成一个包含真实视觉、真实内容、真实交互和真实部署的 Home 页面，比一次生成所有页面更早暴露了 SVG、Figma 状态、浏览器交互与内容管理的问题。这些经验现在可以复用于其他页面。

### 4.2 用户的视觉判断被作为最终标准

多次问题并不是“代码没有实现”，而是“视觉重量、比例、命中区域或动画节奏不对”。坚持回到截图和参考视频进行判断，最终避免了把数值正确误当成视觉正确。

### 4.3 真实设计素材得到保留

最终没有重新手绘替代 Figma 资产，而是修正 SVG 的 viewport、宽高比、内部负偏移和 overflow。Notes 插画的 62×64 定位框与约 77.56×69.38 实际绘图边界就是一个典型案例。

### 4.4 内容系统已经具备扩展基础

中英文 Markdown、Project 独立文件、Notes 预留接口、Home 素材清单和构建校验，使后续页面不再需要把正文和图片配置硬编码进组件。

### 4.5 逐步形成了可验证交付

后期迭代已经包含自动测试、截图证据、浏览器尺寸检查、Git 提交和 Sites 版本。即使某些视觉检查受浏览器截图能力限制，限制也被写入 QA 文档，而不是被隐瞒。

## 5. 可以改进的地方

### 5.1 开发前缺少完整的设计合同

早期只知道组件“看起来应该怎样”，但没有为每个状态一次性记录：节点 ID、容器尺寸、实际矢量边界、overflow、宽高比、颜色变量、动画和命中范围。因此同一组件被多次重新检查。

### 5.2 Figma 结构与代码语义没有始终一致

出现过空容器、旧节点 ID、素材改名、插画放在 Default 而代码用于 Hover 等情况。仅凭图层名称不足以稳定交接；需要节点级链接和状态表。

### 5.3 小改动过早进入线上部署

多次只修改一个尺寸或位置就重新构建和部署。线上地址承担了“开发预览、视觉验收和正式交付”三种职责，拉长了反馈周期。

### 5.4 长任务积累了过多历史上下文

同一任务从参考网站分析一直持续到 Header、内容系统、Home 图片和 Notes。长上下文有利于连续性，但也增加了重复读取、错误沿用旧节点和沟通成本。另一个近似重复任务进一步分散了信息。

### 5.5 共享组件还没有从 Home 页面中完全拆出

Header、主题切换、Contact、绘制圆圈和内容类型目前仍较集中。若直接开始其他页面，容易复制代码或让 Home 页面继续承担全站逻辑。

### 5.6 自动部署尚未完全闭环

GitHub 更新与内容校验已经具备基础，但当前 ChatGPT Sites 正式发布仍需要 Codex 执行。更重要的是，复盘检查时功能代码的本地 `main` 比 GitHub `origin/main` 超前 20 个提交：最新代码已进入 Sites 私有源码和线上版本，却没有完整同步回 GitHub；本复盘随后又新增了一个本地提交。下一阶段应先决定唯一源码真相，并把“提交到 GitHub”“Sites 保存版本”“网站正式发布”三件事明确区分，避免误以为推送 Markdown 后线上站点一定自动更新。

## 6. 五种更简单、更高效地与 Codex 协作的方法

### 方法一：每个 vertical slice 使用一个主任务，并以交接文档开场

下一阶段不要复制当前长任务继续，也不要同时创建两个相似任务。建议：

- 一个页面一个 Codex 主任务；
- 新任务第一条消息引用本复盘文档；
- 明确“本任务只负责哪个页面”；
- 共享组件的改动必须说明会影响哪些已完成页面；
- 页面完成后生成该页面自己的短交接记录。

这样既保留上下文，又避免一个任务无限增长。任务不是按“每一个小修改”拆分，而是按可独立验收的 vertical slice 拆分。

### 方法二：编码前先冻结一页 Design Contract

每个新页面在动手前，先让 Codex 输出并核对一张表：

| 项目 | 必填内容 |
| --- | --- |
| Figma | 页面节点链接、关键组件节点 ID |
| 状态 | Default、Hover、Active、滚动/展开状态 |
| 尺寸 | 容器尺寸、素材实际边界、宽高比 |
| Overflow | 是否允许溢出、是否裁切、负偏移 |
| Token | 字体、字号、行高、字距、Light/Dark 色值 |
| 交互 | 触发区域、点击行为、键盘行为、动画时长 |
| 响应式 | 目标视口与允许的布局变化 |
| 内容 | 对应 Markdown 字段和素材路径 |

确认这张表后再实现。尤其不要只给组件名称，要给节点级链接；改名后也不要继续复用旧节点 ID。

### 方法三：把反馈按“视觉验收批次”提交，减少逐项部署

建议新的迭代节奏：

1. Codex 在本地一次完成一个页面；
2. 生成固定截图矩阵：中文/英文、亮色/暗色、1280×720、1280×900；
3. 用户一次提交 5–10 条带编号的反馈；
4. Codex 在同一批次内全部修复并复检；
5. 通过后只部署一次。

除非问题必须在线上环境才能复现，否则不再为单个 2px 调整单独部署。官方 OpenAI 模型指导也建议使用精简、结果导向的提示词，明确目标、约束、证据和成功标准，并避免在长会话中重复相同指令：<https://developers.openai.com/api/docs/guides/latest-model>。

### 方法四：先提取全站共享壳，再进入 Work 页面

开始下一个页面前，先进行一次有限重构：

- `Header`；
- `ContactMenu`；
- `LanguageSwitcher`；
- `ThemeSwitcher`；
- `DrawnRing`；
- `Footer`；
- 全站 Token；
- 页面内容类型和 Markdown loader。

目标不是大规模重写，而是让 Work、Resume、About 直接复用已验收的 Home 基础。之后每个子页面只需要实现自己的主体内容，避免再次调试 Header。

### 方法五：为每页设置统一 Definition of Done，并把稳定流程沉淀为 Skill

每个页面只有同时满足以下条件才算完成：

- 中文和英文内容均可生成；
- Light/Dark 均通过；
- Desktop 目标视口通过；
- Hover、Active、链接和键盘行为通过；
- 无 SVG 拉伸或裁切；
- 自动测试通过；
- 视觉截图通过；
- 不破坏 Home 回归；
- 只在验收点部署一次；
- 页面交接文档已更新。

当 Work 和 Resume 两个页面都按这套流程完成后，可以把“Figma → Design Contract → 实现 → 截图矩阵 → 回归 → 部署”保存为个人 Codex Skill。OpenAI 官方用例同样建议把重复工作保存为 Skill，并用可评分的改进循环处理困难任务：<https://learn.chatgpt.com/use-cases>。

## 7. 下一阶段推荐顺序

### Step 0：共享基础冻结

先处理两件事：

1. 确认 GitHub 是否作为正式源码真相，并把本地领先的提交安全同步；
2. 拆出全站 Header、Footer、Token、语言/主题状态和内容读取接口。

然后补一个 Home 回归测试，保证重构没有改变已通过的视觉行为。

### Step 1：Work 列表页 vertical slice

优先实现 Work，因为 Project Markdown、封面、顺序和卡片字段已经存在。它能最快验证内容系统是否真正可以扩展到第二个完整页面。

### Step 2：一个 Project 详情页 vertical slice

不要一次做完所有 Project。先选择一个内容最完整的项目，实现详情页结构、图片、正文、导航和响应式；确认模板后再批量接入其他项目。

### Step 3：Resume 页面

Resume 的重点是可重复条目、时间、Label、正文和中英文本地化。它交互较少，适合验证排版系统与 Markdown schema。

### Step 4：About 页面

About 内容结构较简单，但需要控制大段文本的阅读宽度、节奏，以及“关于我 / 关于本站”的信息层级。

### Step 5：Notes

当前继续保持 `work in progress`。等前四个页面稳定后，再启用 Notes 网格和详情页；这样不会在核心求职页面完成前扩大范围。

## 8. 新任务启动前需要准备的材料

- 目标页面的 Figma 节点级链接；
- 页面 Default 状态截图；
- 所有 Hover/Active 状态截图；
- 如果有动画，提供短视频并标注开始、结束和触发方式；
- Light/Dark 设计或明确继承规则；
- 中文与英文 Markdown 初稿；
- 页面使用的真实图片素材；
- 目标桌面视口；
- 本轮明确不做的内容。

## 10. 最终结论

此次 Home vertical slice 的最大价值不只是完成了一个首页，而是建立了后续页面可以复用的四项基础：

1. 已验证的品牌交互语言；
2. 可维护的中英文 Markdown 内容系统；
3. 真实素材的 Figma → Web 处理经验；
4. 自动测试、视觉 QA、版本和部署流程。

下一阶段不需要重新探索这些问题。最重要的工作是先冻结共享基础，再让 Work 页面成为第二个更短、更批量、更可预测的 vertical slice。
